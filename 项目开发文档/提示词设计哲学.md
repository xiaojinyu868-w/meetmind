# 提示词设计哲学：Less Structure, More Intelligence
> 本文档定义 MeetMind AI 工坊所有应用的提示词设计原则，确保提示词与模型能力正交，充分利用模型能力的进步。
---
## 核心思想
**提示词不应该过度约束模型的输出结构和行为细节，而应该清晰描述"要什么"和"为什么"，把"怎么做"留给模型自己推理。**

MeetMind 对输出质量的基本判断是：

> **好的输出 = 个人上下文 + 场景上下文 + 好的模型智能**

- **个人上下文**告诉模型“这是怎样的学习者”：目标、阶段、长期困惑、掌握情况、学习节奏和历史反馈。
- **场景上下文**告诉模型“此刻具体发生了什么”：当前课堂、文章、题目或讨论的真实原件、转录、资料、进度和用户眼前的意图。
- **模型智能**负责判断“现在最应该怎么帮”：解释、定位、复述、连接、检验，或保持克制。

个人上下文是背景，不是命令；场景上下文是当前证据，不是对整个人的定义。发生冲突时，当前用户表达与当前场景优先，长期画像只能帮助理解，不能覆盖用户这一次真正想做的事。

因此，“上下文 > 指令”不是单纯把更多文字塞进 prompt，而是把两类上下文分清、把真实证据给足、把隐私和场景边界守住，再把判断权留给模型。
### 为什么
1. **与模型能力正交** — 模型升级后（qwen-plus → qwen-max → 下一代），同一份 prompt 自动受益于更强的推理能力，不需要重写
2. **避免 prompt 成为瓶颈** — 过度结构化把模型变成"填表机器"，压制其理解力和创造力
3. **面向未来** — 模型越强，过度约束反而拖累模型表现

## 五条设计原则
| # | 原则 | 说明 |
|---|------|------|
| 1 | **描述目标，不描述路径** | 告诉模型"做出世界级的闪卡"，不告诉它"每张卡正面用问句" |
| 2 | **描述用户，不描述格式** | 告诉模型"用户是需要高效复习的大学生"，不告诉它"输出 JSON 数组，每个对象包含6个字段" |
| 3 | **最小结构化** | 唯一需要结构化的是 **前端渲染必须的字段契约** — 这是技术约束，不是智力约束 |
| 4 | **保留创造空间** | 难度分级、题型选择、层次结构等决策让模型自行判断 |
| 5 | **上下文 > 指令** | 把课堂原文完整给模型，让它自己判断哪些值得处理，而不是我们预处理截断 |

## Prompt 两层结构
每个应用的 prompt 严格分为两部分：
### 第一层：渲染契约（不变的，与前端对齐的最小 JSON schema）
这部分是技术性的，必须写——因为前端要解析。但**只定义最外层结构**，不定义内容细节。
```
输出格式：JSON，顶层结构为 { "cards": [...] }
每个 card 必须有 "front" 和 "back" 字段。
其他字段你可以自行添加，如果你认为对学习有帮助的话。
```
> 注意：没有说 front 必须是问句、back 不超过多少字、cards 必须有多少张。
### 第二层：角色与意图（可进化的，与模型能力正交）
```
你是一位深谙认知科学和间隔重复理论的教育专家。
你的学生刚刚上完一堂课，需要你帮他把课堂知识转化为高效的复习闪卡。
目标：让学生通过这些闪卡真正理解和记住核心知识，而不仅仅是机械记忆。
```
> 这段 prompt 不管底层是什么模型，都能让更强的模型产出更好的结果——因为它只描述了"你是谁、用户是谁、目标是什么"，没有限制模型的思维路径。

## 反模式对比
### 旧思路（过度结构化）— 不要这样写
```
你是课堂测验设计助手。请输出JSON格式：
{
"questions": [{
"type": "single_choice",
"question": "问题文本，不超过100字",
"options": ["A选项", "B选项", "C选项", "D选项"],
"answer": "A",
"explanation": "解析，不超过200字",
"difficulty": "easy|medium|hard",
"knowledge_point": "对应知识点"
}]
}
请生成恰好10道题，难度分布为3easy+4medium+3hard。
```
**问题**：规定了题数、难度分布、字数限制、题型、字段枚举。模型变成了填表机器。
### 新思路（Less Structure, More Intelligence）— 应该这样写
```
你是一位经验丰富的命题研究员，擅长设计能区分"真懂"和"以为自己懂"的测试题。
一位学生刚上完一堂课，想检验自己的理解程度。请基于课堂内容，设计一组高质量的测验题。
要求：
- 每道题有 question、options（数组）、answer（正确选项文本）、explanation
- 其他你认为有价值的字段可以自行添加
输出纯 JSON：{ "questions": [...] }
```
**区别**：没规定题数、没规定难度分布、没规定字数限制、没规定题型。让模型根据课堂内容的复杂度和知识点分布**自行判断**。

## 7 个应用的 Prompt 设计方向
| 应用 | 角色定位 | 核心意图描述 | 最小渲染契约 |
|------|---------|------------|------------|
| 精选片段 | 资深课堂编辑 | 找出最值得回看的片段 | `{ highlights: [{ text, startTime, endTime }] }` |
| 课堂摘要 | 学术写作导师 | 帮学生建立课堂全景认知 | `{ summary: string }` (Markdown) |
| 闪卡训练 | 认知科学教育专家 | 设计促进深度理解的闪卡 | `{ cards: [{ front, back }] }` |
| 测验工坊 | 命题研究员 | 设计能检验真实理解的测试 | `{ questions: [{ question, options, answer, explanation }] }` |
| 课堂播客 | 播客主持人 + 嘉宾 | 把课堂变成引人入胜的对话 | 走火山播客专用接口，无自定义 prompt |
| 思维导图 | 知识架构师 | 可视化课堂知识结构 | Markdown 层级大纲（Markmap 直接消费） |
| 信息图工坊 | 信息设计师 | 生成一张值得保存的知识图 | 两步链：文案 prompt → qwen-image-max 生图 |

## 容错策略
弱模型可能因为缺少约束而输出格式不稳定。**应对方案是前端容错，而不是用 prompt 去"管死"模型**：
1. **字段缺失降级渲染** — 如果某个字段缺失，前端用默认值或跳过该卡片，而不是报错
2. **格式兜底解析** — 如果 JSON 解析失败，尝试从文本中提取结构化信息
3. **重试机制** — 格式严重异常时自动重试一次，而不是在 prompt 中反复强调格式
这样的好处：当模型足够强时，容错代码几乎不会被触发；当模型较弱时，容错代码兜底体验。**prompt 永远不需要为最弱的模型而降级设计。**

## 如何评判一条 Prompt 的好坏
✅ 好的 prompt：
- 读起来像是在给一个人类专家布置任务
- 换一个更强的模型后，预期产出质量会自动提升
- 删掉任何一句话都会导致产出变差（没有冗余指令）
❌ 坏的 prompt：
- 读起来像一份填表说明书
- 换更强的模型后，产出质量不会变化（因为被约束锁死了）
- 大量"不要做X"、"必须做Y"的否定/强制指令

## 用户确认是长期记忆的写入合同

模型可以理解意图、提出学习计划、总结这轮形成的进展，但不能自行决定“这就是用户本人”或“以后都应该这样回答”。因此全局 Ask 把智能与控制分成两层：

1. 模型先利用已有课堂与个人上下文生成 `LearningIntentPlan`。意图足够清楚时直接给出理解与第一步；只有答案会明显改变学习路径时，才动态生成 1-3 个单选/多选问题。用户作答后模型吸收选择并自动开始，不把标题、方法和上下文配置表推给用户编辑。
2. 模型输出 `---学习进展---` 只是候选；前端逐条显示，只有用户勾选并确认的内容才能写入 `LearnerProfile.memories`。
3. 应用生成、闪卡/测验操作、普通对话摘要只写 `recentLearningActivities`，作为近期现场线索，不得自动升级为长期身份或偏好。

这不是削弱智能，而是把判断放在正确的一侧：模型负责尽可能理解，用户拥有长期上下文的最终解释权。
