# MeetMind AI 原生应用矩阵实施方案（SSOT）

> 本文档是应用矩阵相关策略、架构、交互、迭代的单一信息源（Single Source of Truth）。
> README 仅保留入口说明，具体细节全部以本文档为准。

## 0. 设计动机（Why，给协作 Agent）

### 0.1 为什么不是继续堆单一 AI 对话

- 单一对话可以覆盖很多功能，但容易失焦：不同层级用户被同一交互路径对待。
- 学习任务本质上需要“执行界面 + 状态回写 + 证据可回放”，纯对话容易状态分叉。
- 结论：对话适合做“路由与澄清”，不适合作为唯一执行容器。

### 0.2 为什么要做应用矩阵入口

- 用户需求天然多样且分层，应用矩阵能把“非用不可”与“锦上添花”分开治理。
- 插件化入口能实现低熵上新：新能力上线不必反复改主流程。
- 结论：应用矩阵是产品形态，不是功能堆叠；目标是可持续迭代能力。

### 0.3 为什么课堂证据链必须是系统不变量

- MeetMind 的单点价值是“课堂原生”，不是通用答题助手。
- 无证据建议会削弱信任，也无法形成“可追责、可复盘、可迁移”的学习闭环。
- 结论：证据链是硬约束，所有关键输出都要可回到课堂原句与时间点。

### 0.4 为什么要先追问再分层

- 用户画像不完整时直接给方案，容易“看起来聪明、实际上不聚焦”。
- 1-2 个高信息量追问可以快速判定用户层级与当前目标，提高命中率。
- 结论：追问不是多问，而是为了减少后续无效交互与错误路由。

### 0.5 为什么动态提示词但不完全自由生成

- 完全硬编码提示词无法适配多样用户；完全自由提示词会导致质量漂移。
- 最稳妥方式是“双层提示词”：固定约束层保证底线，动态层注入个性化上下文。
- 结论：灵活性建立在硬边界之上，不能突破证据链和可追责约束。

### 0.6 为什么 GUI / Tool / Hybrid 要并存

- 不同任务的认知负荷不同：有的要可视化操作，有的只需后台调用。
- 一刀切会导致开发熵增或用户体验失真。
- 结论：按任务本质选择交互形态，闭环核心默认 Hybrid。

### 0.7 为什么强调“只接管不重写”

- L0 能力已实现，重写会制造回归风险和资源浪费。
- 当前收益最高的是统一协议、统一路由、统一状态，而不是重复造轮子。
- 结论：先完成插件化接管，再做能力扩展。

### 0.8 为什么要弱化“困惑点必须标注”

- 让学生主动标注困惑点在很多场景是伪命题，执行成本高且不稳定。
- 在课堂原生路线里，更稳的主线是“全量上下文 + 意图定位 + 证据时间戳”。
- 结论：困惑点是可选增强信号，不是流程前提。

## 1. 目标与边界

### 1.1 总目标

- 在不破坏当前闭环的前提下，把应用上新能力从“改主流程”升级为“加插件”。
- 面向多样化学生需求，做到快速分层、快速聚焦、快速给出针对性学习路径。
- 保持 AI 原生能力增长弹性：模型升级时，应用层不需要大规模重构。

### 1.2 明确边界（避免误解）

- 困惑补救、复习计划、行动清单回写的业务能力已实现。
- 当前阶段不重写这三项能力，只做插件协议接管和统一调度。
- 应用矩阵不是替代主学习流，而是把能力解耦成可复用、可快速上新的系统。
- 默认采用 `Context-first`，不把“先标困惑点”作为入口条件。

## 2. 第一原则：课堂证据链（系统不变量）

课堂证据链是应用矩阵的核心单点，不是可选能力。

### 2.1 强约束

1. 所有 L0/L1 输出必须可追溯到课堂原生内容。
2. 所有关键建议必须带可回放证据（时间戳、原句片段、会话 ID）。
3. 无证据不输出确定性结论，降级为“继续采集/补录/澄清”。
4. 任务完成状态必须绑定证据对象，不允许游离状态。

### 2.2 建议的证据字段（插件输出最小集合）

- `sessionId`
- `anchorId`（可选）或 `citation.startMs/endMs`
- `snippet`
- `action.seek.timestamp`
- `trace`（记录为何选该建议）

### 2.3 证据链质量指标

- `citation_coverage`：有证据引用的输出占比
- `evidence_click_rate`：用户点击证据回放占比
- `unsupported_claim_rate`：无证据确定性建议占比
- `task_trace_integrity`：任务状态与证据对象一致性

## 3. 三层解耦架构

### 3.1 数据输入层（Input Layer）

- 只负责采集，不做重业务决策。
- 统一接入：实时录音、视频导入、转录文本、可选困惑标记、错题数据。
- 核心产物：`InputLayerContext`（raw transcript、anchors、metadata）。

### 3.2 数据记忆层（Memory Layer）

- 负责可检索、可压缩、可演进的记忆快照。
- 当前先做轻量快照：时长、片段数、未解决困惑数、摘要、难点。
- 后续升级 V1/V2/V3 记忆版本时，不影响应用层插件协议。

### 3.3 数据应用层（Application Layer）

- 每个应用都是插件，输入统一上下文协议，输出卡片与任务协议。
- 插件之间不直接耦合，通过注册中心暴露能力。
- 支持显式指定插件或自动路由。

### 3.4 判断能力主线（V0 固定）

- V0 判断能力沿用现有实现：根据用户意图从课堂上下文返回证据时间戳。
- 不依赖长停留、拖动等强行为特征作为核心判断信号。
- 路由优先使用 `transcript/summary + intent`，困惑点仅作可选增强。

## 4. 交互范式（人机交互本质）

默认范式不是“对话套娃”，而是三层分工：

1. 对话层：理解意图、澄清信息、选择路径（Router）。
2. 任务层（GUI）：执行学习动作（Main Workspace）。
3. 助手层：在任务上下文里提供解释与引导（Copilot）。

### 4.1 为什么这样设计

- 降低认知切换成本：用户不会在多层聊天与页面间来回跳。
- 保持可控与可见：任务状态、证据来源、下一步动作都可见。
- 支持多样用户：新手可跟随任务流，进阶用户可直接调插件。

### 4.2 反模式（避免）

- 对话中承载全部执行逻辑，导致状态分叉。
- GUI 与对话入口维护两套任务状态。
- 高风险闭环任务完全黑盒自动执行。

## 5. 应用矩阵入口与小应用模式

### 5.1 入口策略

- 应用矩阵定位：对话主交互的“执行增强层”，不是替代层。
- 应用矩阵采用可开关模式，默认关闭（保守发布策略）。
- 开关作用范围为“当前会话”（session 级）。
- 学生端采用双入口：
  - 智能推荐入口（面向“不知道做什么”的用户）
  - 单应用直达入口（面向“明确要做什么”的用户）
- 应用矩阵是“工作台”，不是“功能墓地”。
- 每个小应用可独立上新/下线，不改核心复习链路。

### 5.2 小应用模式（建议结构）

- 应用选择区：按需求层级与当前目标排序。
- 主任务区：显示当前应用 GUI（若为 GUI/Hybrid）。
- 证据区：显示课堂原句、时间戳、回放入口。
- 助手区：任务内 AI 副驾驶，回答“为什么/怎么做”。

### 5.3 双入口路由规则

1. 用户从智能推荐入口进入：
   - 先做轻量澄清（最多 3 问，推荐 1-2 问）
   - 自动分层并推荐 1-3 个优先应用
2. 用户从单应用直达入口进入：
   - 直接进入目标应用 GUI/Tool 流程
   - 不强制追问，只在关键信息缺失时补问
3. 两条入口共享同一任务与证据状态：
   - 任意入口完成任务后，都回写到统一 `cards/tasks/trace`
   - 不允许“对话里已完成、应用里未完成”的状态分叉
4. 入口显示范围：
   - 仅在复习模式显示应用矩阵入口（课堂上下文优先）
   - 录音模式不显示，避免干扰采集主流程

## 6. GUI / Tool / Hybrid 策略

| 形态 | 定义 | 典型场景 | 默认优先级 |
|------|------|----------|------------|
| `tool` | 后台执行、低交互 | 检索、规划、评分、重排 | 实验与冷启动优先 |
| `gui` | 以可视化操作为主 | 导图、卡片训练、关系浏览 | 认知与体验优先 |
| `hybrid` | tool 产出 + GUI 确认执行 | 知识卡片、困惑补救、错题训练 | 闭环任务优先 |

默认策略：`tool-first` 打通能力，核心闭环任务优先 `hybrid`。

### 6.1 选型四问

1. 是否需要可视化理解？
2. 是否需要用户确认/编辑？
3. 是否可后台自动执行且可验证？
4. 失败是否会直接破坏学习闭环？

判定：

- Q1/Q2 高：`gui` 或 `hybrid`
- Q3 高且 Q1/Q2 低：`tool`
- Q4 高：默认 `hybrid`

## 7. 学生需求分层（L0-L4）

| 层级 | 目标 | 典型应用 | 价值判断 | 默认交互形态 |
|------|------|----------|----------|--------------|
| L0 必需层 | 打通日常学习闭环 | 课堂证据定位、知识卡片回写、行动清单回写（已实现能力接管） | 非用不可 | hybrid |
| L1 提效层 | 提升效率与记忆稳定 | 类 Duolingo 训练、类 Anki 间隔卡片 | 高频复用 | hybrid/gui |
| L2 认知层 | 建立知识结构与迁移 | 思维导图、知识网络、错因聚类 | 深化理解 | gui |
| L3 传播层 | 增强分享与拉新 | 学习战报、成长卡片、同伴激励 | 社交货币 | gui+tool |
| L4 实验层 | 快速试错与创新 | 黑客松灵感应用、限时实验插件 | 低成本验证 | tool-first |

### 7.1 Context-first / Anchor-optional

- 默认工作流：`Context-first`（全量课堂上下文/摘要驱动）。
- 增强工作流：`Anchor-optional`（有困惑标记时提升定位速度）。
- 任何应用都不要求学生先手工标注困惑点。

## 8. 多样用户问题：追问分层 + 画像回写

你提出的核心思路采用如下落地流程：

### 8.1 快速分层流程

1. 首轮检测当前信息是否足够路由。
2. 信息不足时只追问最多 3 个高信息量问题（推荐 1-2 个）。
3. 根据回答与课堂上下文生成用户分层标签。
4. 选择插件和交互形态。
5. 执行后回写画像，下一次减少追问。

### 8.2 追问策略（避免打扰）

- 只问和当前任务强相关的问题。
- 每轮最多 3 问。
- 画像置信度高于阈值时不追问。
- 用户可一键改目标/改层级，防止误分类锁死。
- 问法尽量低负担（优先单选/二选一/短答）。

### 8.3 用户画像（建议字段）

- 学习目标偏好（补漏/提效/冲刺）
- 时间预算（短时/标准/深度）
- 交互偏好（对话优先/任务优先/混合）
- 难度偏好（保守/标准/挑战）
- 证据依赖程度（强证据/轻证据）
- 历史行为信号（完成率、重看率、跳过率，V0 可不启用）

## 9. 动态提示词策略（不硬编码但有边界）

目标是“动态组装”，不是“完全自由生成”。

### 9.1 提示词双层结构

1. 固定层（Hard Constraints）
- 课堂证据链约束
- 不可臆断约束
- 可回放与可追责约束

2. 动态层（Soft Context）
- 用户画像标签
- 当前任务目标
- 最近行为轨迹
- 设备与时段特征

### 9.2 生成策略

- 先分类再组装：先出路由标签，再拼接动态提示词。
- 支持并发候选：多模板并发生成，按质量与时延择优。
- 保留可解释 trace：记录本次提示词来自哪些画像与行为信号。

### 9.3 稳定性保护

- 任何动态提示词都不能突破固定层约束。
- 输出质量下降时回退到稳定模板。
- 对核心 L0 场景启用更严格模板和更短链路。

## 10. 时延预算与性能策略

### 10.1 时延原则

- 优先返回“第一步可执行动作”，其余内容流式补齐。
- 分类、检索、候选计划并行执行。
- 高置信画像直接执行，低置信才追问。

### 10.2 降级策略

- 插件失败：切换 fallback 插件 + 给人工可执行下一步。
- 证据不足：不做强结论，提示补录/补充上下文。
- 超时：先返回最小任务卡，再异步补充细化建议。

## 11. 已落地底座（代码现状）

代码目录：`src/lib/ai-native`

- `types.ts`：执行上下文、卡片/任务协议、插件接口

API：

- `GET /api/apps/plugins`
- `POST /api/apps/execute`

## 12. 版本推进（只接管，不重写）

### V0：闭环接管

- 接入应用矩阵入口与小应用容器
- 接管 L0 数据源到插件协议（Context-first）
- 保持现有行为一致，不改核心业务逻辑
- 首批仅接入 1 个小应用并跑闭环（建议：知识卡片）
- V0 不接入 AI 对话入口，只预留后续对话调用能力

### V1：分层与路由

- 引入“追问分层 + 画像回写”
- 加入动态提示词组装（固定层 + 动态层）
- 加入插件调用埋点与效果看板
- 桌面端优先；统一布局区域可同步移动端，不统一区域后续再适配

### V2：提效与认知扩展

- 上线 L1 卡片学习/间隔复习
- 上线 L2 思维导图/错因聚类等可视化应用

### V3：增长与实验

- 上线 L3 传播型应用
- 建立 L4 实验应用淘汰机制（保留优胜插件）

## 14. 开发与评审验收标准

每个新插件上线前必须满足：

1. 有明确需求层级（L0-L4）与交互形态（gui/tool/hybrid）。
2. 有证据链字段并可回放。
3. 有失败降级路径。
4. 有状态回写策略。
5. 有指标采集与验收阈值。

## 15. Agent 协作检查清单（知其然更要知其所以然）

每次新增/改造应用矩阵能力前，先回答以下问题并写入设计说明：

1. 这个能力解决的是哪一层用户需求（L0-L4）？为什么是这一层？
2. 为什么选这个交互形态（gui/tool/hybrid），而不是另外两种？
3. 关键输出的课堂证据链在哪里（引用字段与回放入口）？
4. 用户画像缺失时要追问什么（最多 3 问，推荐 1-2 问）？为什么是这些问题？
5. 动态提示词的固定约束和动态变量分别是什么？
6. 失败/超时/证据不足时如何降级，避免误导用户？
7. 本次改动是否是“接管”还是“重写”？如果重写，收益是否大于回归风险？

## 16. 需求锁定 v2（已按实现回写）

1. 入口场景：仅复习模式显示应用矩阵入口（录音模式不显示）。
2. 端侧策略：统一区域双端同步已落地（桌面 Tab + 移动端菜单页）。
3. 首批小应用：知识卡片（Context-first）已落地并跑通闭环。
4. 统一协议：插件输出统一为 `cards/tasks/trace`，避免业务状态分叉。
5. 回放一致性：应用矩阵卡片、任务、引用统一走 `handleUnifiedSeek`。
6. 对话关系：保持“对话主交互 + 应用矩阵执行增强层”并存，不做替代。
7. 困惑点策略：困惑点为可选增强信号，不作为入口前提。
8. 判断主线：V0 继续使用“现有意图 -> 时间戳”能力，不依赖长停留行为。
9. 提示词策略：固定硬约束 + 动态软上下文仍为目标，按迭代逐步接入。
10. 开关策略：当前以复习模式入口控制为主，会话级开关能力保留为后续项。
