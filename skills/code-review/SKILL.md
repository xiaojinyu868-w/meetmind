# Code Review

> 完成一组变更后自审，或审查其他 agent 的变更时用。
> 审查的目的是找到会伤用户、伤数据、伤下一个人的问题，不是对照清单打勾。

## 先问三个问题

1. **它做到了声称的事吗？不多不少？** 有新鲜的验证输出（`make check` / 相关 eval / 定向测试 /
   生产 health）支撑，而不是"应该没问题"。
2. **它破坏了什么契约或不变量吗？** 依赖方向、API 薄壳、SSE 事件名与 marker、旧数据回放、
   IndexedDB schema、偏好 key、分享态隐私铁律（不出时间戳 / 不注入访客画像）、用户面文案走 `COPY`。
3. **下一个 agent 会被误导吗？** 代码与 `DOMAIN.md` / `docs/*` / `.env.example` / `CHANGELOG` 一致；
   不显然的取舍写了为什么。

## 然后看这些

- 错误处理：失败路径有意义（用户看到人话，日志留下证据），不是空 catch。
- 安全：没有密钥、token、内部 URL 泄进代码或日志；鉴权没被绕过；用户数据按 `userId` 归属。
- 设计：UI 改动对齐 `docs/DESIGN_SYSTEM.md` 当前版（v7：双签名色、token、**克制的**投影体系）
  与 `docs/PRODUCT_TASTE.md` 原则层。注意旧文档里"零阴影"的说法早已作废。
- 可读性：命名自解释；复杂逻辑的注释说 why 不说 what；≥3 次的重复考虑提取（是考虑，不是必须）。
- 尺度：文件明显变大而没有理由；或反过来，为了行数拆出漏抽象。

## 问题严重等级

| 等级 | 含义 | 示例 | 处理 |
|------|------|------|------|
| **P0 阻塞** | 不修不能交付 | `make check` 报错、运行时崩溃、契约破坏、密钥泄露、隐私铁律 | 立即修 |
| **P1 重要** | 本次应修 | 架构违规、文档与代码不一致、失败路径吞异常 | 当次修 |
| **P2 建议** | 可后续 | 命名、注释、可提取的重复 | 记下来，不阻塞 |

## 输出格式

```
## 审查结果

### P0 阻塞
- [无]

### P1 重要
- `src/xxx.ts:42` — fetch 失败未处理，会变成未捕获异常

### P2 建议
- `src/xxx.ts:15` — `data` 改成 `echoSegments` 更自解释

### 总结
变更 [通过 / 需要修复]，[N] 个问题待处理。验证依据：[列出实际跑过的命令与结果]
```
