# Systematic Debugging

> 遇到 bug、行为不符合预期、测试失败时读。
> 核心只有一句：**假设驱动，证据优先**。可以猜，但每个猜测都要被证据确认或否定后再动手。

## 复现：尽力，但不是前提

- 先找最小复现路径，记下"什么输入 → 什么输出 → 期望什么"。能稳定复现的 bug 最好修。
- **不能本地复现不等于不能修**。这个仓库直接跑在生产服务器上，证据就在手边：
  - pino 日志 `/root/.pm2/logs/meetmind-out.log` / `meetmind-error.log`（结构化 JSON，按 `tag` 过滤）
  - 事件日志 `data/teach-events/`、`data/fenshen-events/`（SSE 回放）
  - Sentry（`docs/OBSERVABILITY.md`）、`pm2 describe meetmind`、`/api/health`
  - 浏览器侧：IndexedDB 是客户端真相源，用户机器上的状态可能与服务端不同
- 用这些证据重建时间线。竞态、上游 500、跨设备状态漂移这类问题多半只能这样定位。
  基于证据修复时，在提交说明里写明"未本地复现，依据 X 日志 / Y 事件"。

## 定位：读源码，逆推调用链

- 从错误信息出发逆向追调用链；grep 找相关代码；读足够上下文理解完整逻辑。
- `DOMAIN.md` 告诉你去哪找，源码告诉你真相。两者不一致时以源码为准并顺手修文档。
- 区分三种"坏"：数据坏（旧数据 / 迁移）、契约坏（两端对不上）、逻辑坏。修法完全不同。
- 一个信号可能有多个成因。改状态、重启、删数据之前，确认证据真的指向这个动作，
  而不是"模式匹配到了一个熟悉的故障"。

## 修复：最小但完整

- 修根因，不修症状。如果根因在别处（上游契约、旧数据），修那里；实在修不了就加护栏并写明。
- 需要多处协同的修复就一起改——"一次只改一行"不是原则，"每一处都知道为什么改"才是。
- 修复与重构分开提交；修复过程中发现的其他问题记下来，不顺手扫进同一个提交。
- 每一步 `make check`；涉及 ASR / Tutor / teach 链路的修复跑对应 `make eval-*`。

## 验证：证明它消失了

- 用复现路径（或生产证据的等价物）验证 bug 消失；有条件就补一个回归测试。
- 检查 import 这段代码的其他地方没有被连带改坏。
- 生产上验证：部署后看 health、看日志里那条报错是否不再出现。

## 常见陷阱

| 陷阱 | 正确做法 |
|------|---------|
| 改了没验证就改下一处 | 每一处都有证据说它改对了 |
| 同时改三个可疑位置，最后不知道哪个起效 | 分开验证；确实需要协同修改时，说清每一处的作用 |
| 调试 `console.log` 留在代码里 | 用 `createLogger`，或调完删掉 |
| 没有证据就宣布根因 | 假设 → 找证据 → 确认 → 再动手 |
| 修复顺手重构 | 分开提交 |
| "不能复现，所以放着" | 用生产证据重建时间线；加可观测性；写明依据 |
| 看到重启次数 / 报错就重启服务 | 先查 pm2 日志确认是崩溃循环还是部署计数；没证据不动生产 |
