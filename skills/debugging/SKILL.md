# Systematic Debugging

> 本 skill 定义系统化的调试流程。禁止"猜+试"式调试。

## 触发条件

- 遇到 bug 或错误时
- 行为不符合预期时
- 测试失败时

## 四阶段流程

### 1. Reproduce（复现）

在做任何修改之前：
- 找到最小的复现步骤
- 确认错误信息的完整内容
- 记录：什么输入 → 什么输出 → 期望什么输出

**规则**：如果不能复现，就不能修复。先让它稳定复现。

### 2. Locate（定位）

缩小范围到具体代码：
- 从错误信息开始，逆向追踪调用链
- 用 `search_content` 找到相关代码
- 读上下文（前后 30 行），理解完整逻辑
- 确认：bug 在哪一行/哪个函数？

**禁止**：
- 不要一上来就改代码
- 不要同时修改多个可疑位置

### 3. Fix（修复）

最小化修复：
- 只改导致 bug 的那一行/那个逻辑
- 如果修复涉及多个文件，一个文件一个文件地改
- 每改一个文件立即 `tsc --noEmit`

**规则**：
- 修复不能引入新行为（只修 bug，不加功能）
- 修复后文件不能变大超过 10 行

### 4. Verify（验证）

确认修复有效：
- 用步骤 1 的复现路径验证 bug 已消失
- `tsc --noEmit` 零错误
- 确认没有破坏其他功能（检查 import 这个文件的其他地方）

## 常见调试陷阱

| 陷阱 | 正确做法 |
|------|---------|
| 改了代码没验证就继续改下一个 | 每改一处立即验证 |
| 同时改三个可疑位置 | 一次只改一个，验证后再改下一个 |
| 把调试 console.log 留在代码里 | 用 `createLogger` 或调试完删掉 |
| 猜测根因就开始改 | 先复现，再定位，确认后再改 |
| 修复的同时"顺便"重构 | 修复和重构分开提交 |
