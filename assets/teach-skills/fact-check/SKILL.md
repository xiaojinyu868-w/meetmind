# 事实核查

> 上游：THU-MAIC/OpenMAIC（MIT）`skills/agent-runtime/fact-check/SKILL.md`，2026-09 vendor，合规说明见 `../NOTICE`。
> 裁剪：删除 list_scenes/read_stage/patch_stage/pro-editing 等课件编辑工具引用与 ask_user 表单门禁（确认走自然口播）；web_search/fetch_url 联网核查在本引擎不可用，按上游自带的"无联网工具"降级路径展开为正式纪律。短名单核查纪律、已认可输入保护、报告格式原样保留。

把严重事实错误和 AI 幻觉挡在课堂之外，同时不把上课变成 exhaustive 审计。聚焦少数真正影响信任的主张。

本引擎**没有联网核查工具**。因此默认纪律是：用稳定知识教学、少做事实承诺、对 genuinely 不确定的主张显式标记（口播说"这个我不完全确定，课后我们查证"），绝不编造来源、数字或引文。

## 讲课过程中的实时纪律

讲解、出题、判分时，心里维护一份高信号风险短名单：

- 精确数字、日期、计数、人名、归属引文；
- 定律、标准、公式、技术定义与分类；
- "第一""唯一""总是""必须"式绝对化主张；
- 被当作定论陈述的因果或专业结论；
- 与前面讲过内容相矛盾的表述；
- 可疑地精确、又拿不出支撑的主张。

不要核查每一个主张。跳过正确的内容、措辞偏好、无害的简化和低价值冷知识。

短名单上的主张：若属于稳定常识，照讲；若有任何迟疑，降级表述（"主流观点认为……""截至我了解的范围……"）或显式标记待查。**宁可少说一个精确数字，不可说错一个。**

## 应要求核查已有内容时

学生拿着一段内容（板书、讲义、题目、他自己的笔记）要求核查时：

1. 先报告发现，经学生口头确认后再改板书；除非修改本来就是请求的一部分。
2. 报告给 3–8 条有用发现（更少就如实更少），按三组归类、空组省略，口播说出、要点落板：
   - **A. 明确事实错误**
   - **B. 表述不严谨**
   - **C. 需要核实** — 只在主张重要时列出
3. 每条发现说清三件事：**原始表述**（只引相关句子）、**存在问题**（错在哪、正确事实是什么）、**修改建议**（只说改法）。不展示分数、置信度、方法论，不罗列正确的内容，不凑数。没发现实质问题就说明核查范围并讲"未发现明显错误"，不宣称内容完全准确。

## 保护已认可输入

不做与学生既定课程计划、学生自己提供的材料或学生明确给出的事实相冲突的"纠正"。这些是经认可的输入，不是普通生成文本。

如果证据显示已认可输入本身可能有误：不要直接改，也不要默默覆盖。口头指出冲突——哪个主张、相反证据是什么——给学生选择：保留原输入、授权按事实更正、或仅标记分歧暂不改。

## 边界

- 核查不了就说核查不了。"找不到可靠证据"不等于"是假的"；核实没有结论时如实说，不编造判决或更正。
- 本 skill 不管语法、文风、排版。
