# MeetMind 服务器 Agent 交接文档（Capture V1）

更新时间：2026-03-09

这份文档给服务器上的 agent 直接读。目标不是解释一堆历史背景，而是让 agent 在服务器上继续开发、联调、验收时，**严格对齐产品定义和当前实现方向**。

---

## 1. 先说结论

当前阶段，MeetMind 最重要的不是做更多 AI 页面，而是把 `收集` 这一块做成真正成立的产品。

当前版本的北极星是：

**MeetMind Capture = 一个微信式的学习上下文聊天流。**

用户只是在把学习现场里的东西发给 MeetMind：

- 左边发原声
- 输入框里做语音转文字
- `+` 统一上传文件、图片、视频、文档、链接
- 所有内容都先像消息一样进入流
- 后台再异步转录、OCR、解析、发酵
- 原来“单节课时间轴复习”的能力继续保留，并自然挂在音频/视频消息后面

---

## 2. 创始人意图：产品到底要做成什么

### 2.1 产品不是录音工具

不要把 `收集` 理解成“录音 tab”或“导入工具页”。

它应该是：

- 一个以聊天为语法的收集器
- 一个把学习现场的原始材料自然收进来的地方
- 一个以后能长出回声、Tutor、复习的上游入口

### 2.2 先做好收集，AI 先后置

当前阶段，产品定义更接近：

- 学 `flomo`：学“顶级收集应用”的心智和低摩擦
- 不学 flomo 的 AI 洞察前台
- `AI` 先退到后台做辅助，不要抢主流程

现在不要把主页面做成 AI 展示页。
现在要做的是：

- 收集
- 原件保留
- 异步解析
- 兼容复习

### 2.3 微信是交互语法，不只是 UI 参考

重点不是“长得像微信”，而是“用起来像微信”。

必须坚持：

- 左侧一个稳定的原声入口
- 输入框内一个稳定的听写入口
- `+` 是统一上传，不做音频/材料/视频分类
- 历史不放在 `+` 里
- 发送按钮心智稳定
- 上传和发语音后先进入流，再后台处理

### 2.4 原件优先

任何输入都不要被 AI/解析结果吞掉。

原则：

- 原声先保留原始音频
- 图片先看原图
- 文档先开原件
- 视频先保留原视频
- 解析结果主要服务后台、Tutor、回声，不默认抢主消息

### 2.5 兼容旧核心能力

以前产品里最有价值的一条链不能丢：

- 单节课长音频/视频
- 时间轴/时间戳
- 课堂问答
- 进入复习

新形态不是替换旧能力，而是包住旧能力。

理想状态：

- 用户像发微信一样发一条长语音/视频/音频文件
- 这条媒体消息留在收集流里
- 转录完成后，下面自然出现 `去复习`

### 2.6 回声是轻反馈，不抢主流

`回声` 有价值，但不能打断主收集流。

原则：

- 主流先负责收集
- 回声只做轻提示、折叠入口、独立入口
- 不要在收集主页面里长期堆大块 AI 洞察卡

### 2.7 用户是谁

当前优先人群不是 K12。

先服务：

- 本科高年级
- 研究生
- 保研/绩点/科研/申请/读文献这类高自主学习者

这类用户更适合重上下文、重材料、重复习、重回看。

## 3. 当前阶段的产品边界

### 3.1 这阶段重点做什么

只聚焦 `Capture First`：

- 微信式收集流
- 原声/听写/文件/图片/链接统一输入
- 原件消息先进入流
- 后台异步转录/OCR/解析
- 历史收集
- 原件打开
- 与原有复习页兼容

### 3.2 这阶段不要重点做什么

不要优先做：

- 复杂 AI 前台
- 大画像展示
- 多个一级页面扩张
- 花哨洞察
- 过度自动化人格交互

一句话：

**先把“我什么都能顺手丢进来，而且一点都不累”做成立。**

## 4. Capture V1 的理想形态

### 4.1 页面是什么

`收集` 页应该是：

- 一个聊天式内容流
- 一个稳定底部输入栏
- 一个轻量侧边系统（历史、回声、累计）

不是：

- 工作台
- 导入面板集合
- AI 功能页
- 表单上传页

### 4.2 输入语法

用户主观感受应该永远是：

**我只是给 MeetMind 发消息。**

当前应该支持的输入语法：

- `text`
- `dictation_text`
- `raw_voice`
- `image`
- `file`
- `video`
- `link`

### 4.3 每种消息的产品语法

#### 文字
- 发出即进流
- 不需要系统 toast

#### 听写
- 输入框内右侧按钮触发
- 文字直接追加到输入框
- 不抢左侧原声入口

#### 原声
- 左侧稳定入口
- 停下后先发原始音频消息
- 聊天栏立刻恢复
- 转录在后台继续跑
- 转录成功后再长出 `文字 / 去复习`

#### 图片
- 点击图片直接查看原图
- 主消息默认只看图
- OCR 默认不在主消息展示全文

#### 文档/PDF/PPT
- 先像原件消息一样进入流
- 用户点开原件
- 解析留后台慢慢完成
- 不在主消息展示解析正文

#### 视频/音频文件
- 先像媒体消息一样进入流
- 后台提取音轨、转录、建时间轴
- 成功后自然出现 `去复习`

## 5. 服务器 agent 必须遵守的产品守则

### 5.1 不要回退成分类上传

不要重新引入：

- 音频上传
- 材料上传
- 视频上传

三种分类入口。

`+` 必须是统一上传。

### 5.2 不要在主消息展示解析正文

以下内容不要默认放在主消息里：

- 图片 OCR 全文
- 文档解析全文
- 视频摘要全文

主流应该看原件，不看处理结果。

### 5.3 不要让系统反复解释自己

尽量避免在前台出现：

- “文件已加入当前收集流”
- “系统会在后台继续解析”
- “已接入，可用于后续理解”

这些都太像系统日志，不像产品。

### 5.4 不要破坏旧复习能力

任何对媒体消息的改动都要保证：

- 音频/视频成功解析后仍能进入复习
- 时间轴/时间戳不被切断
- 旧的课堂问答能力可继续消费这些材料

### 5.5 不要让处理过程阻塞继续输入

必须保留这条产品原则：

- 原件先发出去
- 解析异步进行
- 用户可以继续发下一条

## 7. 服务器部署前提

### 7.1 基础环境变量

至少要有：

- `DATABASE_URL`
- `DASHSCOPE_API_KEY`

### 7.2 让音频/视频转写真正工作

以下变量非常关键：

- `PUBLIC_DOMAIN` 或 `PUBLIC_HOST`

原因：

- `/api/transcribe`
- `/api/transcribe-fast`
- `/api/transcribe-turbo`

都需要给外部转写服务一个**公网可访问的文件地址**。本地联调时如果没有公网地址，就会出现：

- `ASR_PUBLIC_HOST_MISSING`
- 或外部服务拉不到文件

服务器部署时必须保证：

- 应用对外有稳定 HTTPS 域名
- 公开静态文件可从外部访问
- `public/temp-audio/*` 这类路径能被上游服务读取

### 7.3 微信登录（可选）

如果服务器上要联调微信登录：

- `NEXT_PUBLIC_ENABLE_WECHAT_LOGIN=true`
- `WECHAT_REDIRECT_URI=https://你的域名/api/auth/wechat/callback`

### 7.4 微信服务号轻录入（可选但推荐）

如果服务器上要联调服务号录入：

- `WECHAT_MP_TOKEN=...`
- `WECHAT_MP_PUBLIC_BASE_URL=https://你的域名`

当前代码默认按**明文模式**来接公众号消息，不是 AES 加密模式。

### 7.5 Prisma

当前 `prisma.config.ts` 从 `DATABASE_URL` 读数据库连接。

如果服务器仍然用 SQLite，要确保路径和权限正确。
如果改成 MySQL/Postgres，需要由服务器 agent 自己迁移并验证。

## 8. 当前已知的“本地 vs 服务器”差异

### 8.1 本地为什么很多原声不能进入复习

不是按钮丢了，而是：

- 本地没有公网可访问地址
- 转写服务拉不到本地临时文件
- 转写失败
- 所以不会长出 `去复习`

这是当前已知行为，不是核心产品设计错误。

### 8.2 本地图片解析和服务器表现可能不同

图片链已经做了稳定性优化，但图片识别仍依赖服务端图片导入接口。
服务器联调时要重点验证：

- 常见 PNG/JPG/JPEG
- 手机截屏
- 图片过大时的失败态

### 8.3 服务号不是重材料入口

公众号聊天里不能当成“任意文件附件系统”。

当前正确分层是：

- 服务号：文字、语音、图片、链接
- H5/Web：PDF、课件、录音文件、深交互、Tutor、回声

## 9. 服务器 agent 上线后的第一轮联调清单

### 9.1 核心路径必须全测

1. 打开 `/app?mobile=1`
2. 发一条文字
3. 发一段原声
4. 上传一张图片
5. 上传一个 PDF
6. 上传一个 PPT/PPTX
7. 上传一个音频文件
8. 上传一个视频文件
9. 验证消息是否都**先进入流**
10. 验证后台解析时是否**不阻塞下一次输入**

### 9.2 原声 -> 复习链

重点验证：

1. 左侧原声录制
2. 停止后原始音频消息立即进入流
3. 聊天栏立即恢复
4. 后台转写成功
5. 这条消息自然出现 `文字 / 去复习`
6. 点 `去复习` 能进入原有复习页，并带上时间轴/时间戳

### 9.3 图片链

重点验证：

1. 主消息只看图
2. 点图直接看原图
3. OCR 不抢主消息
4. Tutor/回声仍然能消费图片内容

### 9.4 文档链

重点验证：

1. 文档先像原件消息进入流
2. 点消息能打开原件
3. 不展示解析全文
4. Tutor 后续可消费解析结果

### 9.5 微信服务号链

重点验证：

1. 服务号发送文字/语音/图片/链接
2. 自动回复里拿到 capture 链接
3. 打开 H5 承接页
4. 再进 `/app?mobile=1&wechat_capture=...`
5. 内容成功进入当前工作区收集流

## 10. 当前阶段最值得继续开发的东西

服务器 agent 如果要继续往前推，优先级这样排：

### P0
- 跑通 `原声 -> 转写 -> 去复习`
- 跑通 `视频文件 -> 后台解析 -> 去复习`
- 保证所有原件消息先入流、解析不阻塞

### P1
- 统一媒体消息语法，让图片/文档/视频/音频都更像“原件消息”
- 继续削掉系统话术
- 继续隐藏不必要的中间处理状态

### P2
- 把 `回声` 做成真正的“回来理由”
- 开始做跨课、跨材料、跨 session 的连接

---

## 11. 当前阶段不要做的事

服务器 agent 不要把时间花在这些方向：

- 重做 AI 洞察前台
- 大幅扩展 Tutor 页面
- 引入新的复杂一级页面
- 回到分类上传
- 在主流展示 OCR/解析全文
- 重做“功能工作台”

如果改动会让产品更像“系统功能集合”，就偏了。

---

## 12. 给服务器 agent 的一句话指令

如果你只记一件事，就记这一句：

**继续把 MeetMind 的 `收集` 做成一个微信式、原件优先、异步发酵、兼容单节课复习的 Capture First 产品，不要让 AI 和系统解释抢走主流。**
