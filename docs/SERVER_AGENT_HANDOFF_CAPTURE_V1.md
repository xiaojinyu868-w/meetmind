# MeetMind Agent Handoff: Capture V1

更新时间：2026-03-11

这份文档给下一个对话里的 agent 直接阅读。
目标不是只交代“当前改了什么”，而是把下面三层一次性交代清楚：

1. 用户对整个产品的完整定义和长期意图
2. 当前阶段为什么先聚焦 `收集`
3. 当前实现到了哪里、下一步该怎么走

---

## 1. 一句话定义

当前阶段，MeetMind 最重要的不是继续扩更多 AI 页面，而是把 `收集` 做成一个真正成立的产品。

**Capture V1 = 一个微信式的学习上下文聊天流。**

用户只是把学习现场里的内容发给 MeetMind：

- 左边发原声
- 输入框里做语音听写
- `+` 统一上传图片、文档、音频、视频、链接
- 所有内容先像消息一样进入流
- 后台再异步转录、OCR、解析、发酵
- 媒体消息成熟后，自然长出 `去复习`

旧的核心能力不能丢：

- 单节课长音频 / 视频
- 时间轴 / 时间戳
- 课堂问答
- 复习模式

新形态不是替换旧能力，而是把旧能力包进新的收集语法里。

## 1.5 用户的完整产品定义与长期意图

这部分非常关键。下一个 agent 不能只把当前任务理解成“修一个录音页”，必须理解用户真正想做的产品。

### 1.5.1 用户不想做什么

用户不想做的是：

- 一个“AI 教育工具”外壳
- 一个“录音转写工具”
- 一个“功能工作台”
- 一个“功能矩阵越堆越多”的应用
- 一个前台满是 AI 解释和提示的产品

用户明确反感：

- 强引导
- 选择题式问卷
- 分类上传
- 模式切换感很重
- 工具/控制台味太重
- 前台大量系统解释文案
- 明明可以后台做，却要让用户先做决策

### 1.5.2 用户真正要做什么

用户真正要做的是：

**一个以个人学习上下文为核心的产品。**

核心不是“回答问题”，而是：

- 先把学习现场收进来
- 保留原件
- 在后台慢慢理解
- 再自然长出复习、Tutor、回声、画像、跨材料连接

也就是：

**先收，再懂，再教。**

### 1.5.3 长期产品北极星

长期来看，MeetMind 不是一款单点应用，而是：

**一个以学习者长期上下文为中心的学习产品 / 学习基础设施。**

它最终要做到两件事：

1. AI 真正“听过这节课、看过这些材料、接触过这些原件”
2. AI 真正“越来越懂这个人如何学习、在乎什么、卡在哪里”

长期完整形态应自然长出：

- Capture（收集）
- Review（复习）
- Tutor（深交互）
- Echo（轻回声 / 发酵）
- 跨课、跨材料、跨 session 的连接

### 1.5.4 当前为什么先做 Capture

用户当前已经明确：

- 不先做前台 AI 炫技
- 不先做复杂画像展示
- 不先做很多一级页面
- 不先做“大而全”的多端系统

原因很明确：

**如果用户没有自然地把学习现场收进来，后面所有智能都没有基础。**

所以当前阶段必须是：

**Capture First。**

## 2. 产品北极星

### 2.1 产品不是什么

不要把当前主产品理解成：

- 录音工具页
- 上传工具页
- AI 工具页
- 工作台 / dashboard
- 功能入口集合

### 2.2 产品是什么

当前更准确的定义是：

**MeetMind Capture = 一个 Capture First 的学习上下文收集器。**

它像微信一样自然输入，像 flomo 一样低摩擦收集，但最终会自然长出：

- 复习
- Tutor
- 回声
- 跨材料连接

### 2.3 当前阶段优先级

先把 `收集` 做到极好，AI 尽量后置。

当前阶段重点不是：

- 前台大块 AI 洞察
- 复杂画像展示
- Tutor 多入口扩展
- 新的一堆一级页面

当前阶段重点是：

- 极低摩擦收集
- 原件优先
- 异步解析
- 与旧复习能力兼容

### 2.4 这个阶段的灵感来源怎么分工

用户已经明确过，不同产品学不同东西：

#### 学 flomo 的是

- 好的收集哲学
- 极低摩擦记录
- 原件优先
- AI / 洞察后置
- 每日回顾和“回来理由”
- 微信输入作为一级入口

#### 学微信的是

- 交互语法
- 输入习惯
- 发送即落地
- 语音、图片、文件、链接都像消息一样存在

#### 学 Elys 的是

- 后续的关系感
- 引导式建档
- 画像建立方式

但 **Elys 不是当前第一优先级**。当前第一优先级还是：

**把一款顶级的收集应用做好。**

## 3. 产品原则

### 3.1 微信式交互语法

用户不应该先想“我现在在用哪个功能”，他只是在“发给 MeetMind”。

稳定语法：

- 左侧：`原声`
- 输入框：文本输入
- 输入框内右侧：`听写`
- `+`：统一文件入口
- 右侧：`发送`

### 3.2 原件优先

任何输入都不应该被解析结果吞掉。

原则：

- 原声先保留原始音频
- 图片先看原图
- 文档先开原件
- 视频先保留原视频

解析结果主要服务后台、Tutor、回声，不应默认占主消息。

### 3.3 先收，后理解

所有输入都应该：

1. 先进入收集流
2. 再后台异步处理
3. 不阻塞下一次输入

用户前台只需要明确感知：

- 我刚刚发出去了
- 它已经被收下

而不是看到系统解释自己做了什么。

### 3.4 不要系统话术抢戏

尽量避免在主流里出现下面这种话：

- 文件已加入当前收集流
- 系统正在后台解析
- 已接入，可用于后续理解
- 当前环境暂不支持……

如果必须提示，也应尽量轻、人话化，并放在次级位置。

### 3.5 兼容旧复习能力

任何媒体消息相关改动，都不能破坏：

- 音频 / 视频进入复习
- 时间轴 / 时间戳
- 课堂问答

理想状态：

- 用户先发一条媒体消息
- 后台转写完成
- 消息下面自然出现 `去复习`

### 3.6 回声和画像的边界

用户的判断非常明确：

- 回声有价值
- 但不能霸占主页面
- 画像有价值
- 但不应该前台做成标签展示

正确做法：

- 主流负责 `收`
- 回声负责 `发酵`
- Tutor 负责 `深挖`
- 画像主要是后台能力，不是前台主内容

AI 的职责是：

- 收集后的理解
- 后台解析
- 轻回声
- Tutor 上下文准备

而不是在前台不断打断用户。

### 3.7 当前 UI/交互判断标准

后续任何改动，都要拿这几句校验：

1. 这个改动是不是让用户更容易收集？
2. 是不是更原件优先？
3. 是不是更少打扰？
4. 是不是更像“发消息”，而不是“用功能”？
5. 是不是更容易自然长出复习和 Tutor？

只要偏离这些，就说明方向跑偏了。

## 4. 当前理想形态

### 4.1 页面结构

`收集` tab 应该像一条聊天式内容流：

- 顶部：很轻的聊天页头部
- 中间：内容流本身
- 底部：稳定输入栏
- 侧边：历史 / 回声 / 全部收集 / 微信输入 这类收集系统入口

不应该像：

- dashboard
- workbench
- 表单上传页
- AI 展示页

### 4.2 支持的消息类型

当前消息对象应统一成：

- `text`
- `dictation_text`
- `raw_voice`
- `image`
- `file`
- `video`
- `link`

每种消息都应先有“原件消息态”。

### 4.3 各类输入的理想行为

#### 文本

- 直接发送
- 立刻进入流

#### 听写

- 输入框内右侧按钮触发
- 文本直接追加到输入框
- 不抢原声入口

#### 原声

- 左侧固定入口
- 录一整段
- 停止后先发原始音频消息
- 聊天栏立刻恢复
- 转录后台跑
- 转录成功后自然长出 `看文字 / 去复习`

#### 图片

- 支持相册选择、文件选择、桌面粘贴
- 主界面默认只看图
- 点击直接看原图
- OCR 默认不在主消息展开

#### 文档 / PDF / PPT / PPTX

- 先作为原件消息进入流
- 点击打开原件
- 后台慢解析
- 不在主消息默认展示解析正文

#### 音频 / 视频文件

- 先作为媒体消息进入流
- 后台转录 / 提取 / 建时间轴
- 成功后自然长出 `去复习`

- 音频文件上传不再固定走 `/api/transcribe-turbo`

  - 缺公网时 fallback 到 `/api/transcribe-turbo`

  - 停止后先把原始音频消息发进流

  - 浏览器原生语音识别优先

  - 不再依赖 `/api/asr-stream` WebSocket
- 视频链接发送现在是：
  - 先插入一条 optimistic 视频消息
  - 后台再补标题 / 封面 / 时长 / `去复习`
- 图片 / 文档主消息已改成原件优先

  - 文档只看原件
  - OCR / 解析正文默认不在主流展示
- 35 秒音频这类本地媒体时长，不再首屏错误显示成 1 秒
  - 收集页和复习页会优先取本地媒体时长
- 本地原声 / 音频失败态已经收轻
  - 例如只显示 `原声已保留`
  - 不再重复刷“暂时不能进入复习”之类文案

## 6. 当前仍未完全闭环的点

### 6.1 原声 / 音频 -> 转写 -> 去复习

这是当前最重要的闭环。

现状：

- 消息先发出去已经成立
- 本地 fallback 已补
- 但完整的“转写成功后自然长出 `去复习`，并稳定进入原复习页”仍需要服务器环境联调验证

### 6.2 视频文件媒体语法

视频已经能进统一上传链，但仍需要继续打磨：

- 更像真正的媒体消息本体
- 更自然地进入复习

### 6.3 回来理由

历史、回声、全部收集已有骨架，但还没有完全形成 flomo 式“回来继续记”的复利感。

### 6.4 当前最脆弱的链路

下一个 agent 不要对下面这些链路过度乐观：

- `听写`
  - 当前已改成：浏览器原生语音识别优先；原生不可用时，退化为“录一整段 -> `/api/transcribe-turbo` -> 再补到输入框”
  - 代码已经接上，但仍需要继续本地实测不同浏览器
- `原声 -> 转写 -> 去复习`
  - 消息先发出去已经成立
  - fallback 已经补上
  - 但服务器环境下的完整闭环仍需验证
- `视频链接 / 视频文件 -> 去复习`
  - 已接入主路径
  - 但消息语法和复习恢复链仍然是高风险区域
- `page.tsx`
  - 仍然非常大
  - 任何改动都可能影响别的分支逻辑
  - 下一个 agent 在这里动手要特别克制

## 7. 本地开发与服务器联调的区别

### 7.1 本地开发已能做的

- 聊天式收集流 UI 打磨
- 统一上传链
- 图片 / 文档 / 视频 / 链接消息语法
- 原声先发消息
- 听写 fallback
- Capture / Workspace / Echo 语义层开发
- 微信入口骨架开发

### 7.2 服务器联调必须验证的

- 原声 / 音频文件的公网可访问转写链
- 视频 / 音频转写成功后 `去复习`
- 微信服务号真实回调
- 微信发来的内容进入同一工作区收集流

### 7.2.1 服务器上必须明确配置的环境变量

下一个 agent 在服务器上先确认这些再联调，不要先盲测：

- `DASHSCOPE_API_KEY`
  - 转写、文档解析、图片理解都会用到
- `PUBLIC_DOMAIN` 或 `PUBLIC_HOST`
  - 原来的 filetrans 路线需要公网可访问地址
- `WECHAT_MP_TOKEN`
  - 服务号消息推送验签
- `WECHAT_MP_PUBLIC_BASE_URL`
  - 服务号回执里的 H5 链接基址

如果要继续做微信绑定 / 网页授权，还要确认：

- `WECHAT_APP_ID`
- `WECHAT_APP_SECRET`
- `WECHAT_REDIRECT_URI`

如果缺这些值，不要把联调失败误判成产品链路坏了。

### 7.3 微信服务号在整个产品里的角色

用户已经明确：

- `微信服务号 = 轻录入入口`
- `H5 / Web = 深交互入口`

服务号负责：

- 文字
- 语音
- 图片
- 链接

H5 / Web 负责：

- 看原件
- 补材料
- 复习
- Tutor
- 回声
- 工作区上下文

不要把服务号理解成完整产品，它是最自然的“轻收集入口”。

### 7.4 已验证 / 未验证矩阵

这部分非常重要。下一个 agent 不要把“代码已写”误判成“链路已验证”。

#### A. 代码已实现 + 本地已多次验证

- 聊天式收集主路径
- 左原声 / 框内听写 / `+` 统一上传 / 稳定发送按钮
- 图片原图优先
- 文档原件优先
- 文件先入流、后台慢解析
- `全部收集 / 历史收集` 的内容化入口

#### B. 代码已实现 + 本地部分验证

- 听写 fallback：原生识别失败后退化为整段录音转文字
- 原声先发原始音频消息，再后台转写
- 统一上传链对图片 / 文档 / PPT / 音频 / 视频 / 链接的接入
- Capture / Workspace / Echo 的服务端骨架
- 视频链接 optimistic 消息 -> 后台补全标题 / 封面 / 时长 / `去复习`
- 原件优先语义：
  - 图片默认看原图
  - 文档默认开原件
  - 解析结果默认不占主消息
- 本地媒体时长优先取原件时长，不再首屏把 35 秒音频误显示为 1 秒

#### C. 代码已接上 + 服务器环境未完全验证

- 原声 / 音频文件 -> 转写成功 -> `去复习`
- 视频文件 / 视频链接 -> `去复习`
- 微信服务号真实回调
- 微信消息进入同一工作区收集流
- H5 承接页与工作区 capture 的完整闭环

#### D. 仍需继续产品化打磨

- 回来理由（历史 / 回声 / 每日回看）

### 9.3 Capture V1 验收清单

下一个 agent 可以直接用这份清单做验收，不要只看感觉。

#### 输入与落地

- 发一段原声，消息立即出现
- 停止原声后，输入栏立刻恢复
- 听写至少在当前环境中可用：
  - 原生语音识别可用时实时追加
  - 原生不可用时可退化为整段录音再补文字
- 上传图片 / 文档 / 音频 / 视频，不阻塞继续发下一条
- 发送链接时，消息先出现，后台再解析

#### 原件优先

- 图片默认只看原图
- 文档默认只看原件
- 原声默认保留原始音频
- 解析结果不默认占主消息

#### 媒体与复习

- 音频 / 视频转写成功后，消息自然长出 `去复习`
- `去复习` 能进入正确的复习态，而不是回落到示例内容
- 本地失败态不露技术细节

#### 收集系统

- `全部收集` 能作为真实内容入口使用
- `历史收集` 能继续一条已有收集
- 微信发来的内容最终能进同一条收集流

#### 体验

- 主界面更像聊天，而不是工作台
- 失败态、处理中、空态都不系统化
- 用户不需要先思考“我该用哪个功能”

### 9.4 上服务器前 smoke test 清单

下一个 agent 在本地或服务器上，至少要手跑这一组：

1. 原声录制
   - 开始录制
   - 停止后消息立即出现
   - 聊天栏立即恢复
   - 转写回来后出现 `看文字 / 去复习`
2. 音频文件上传
   - 上传后消息立即出现
   - 首屏时长正确
   - 转写回来后出现 `去复习`
3. 视频链接发送
   - 发送后消息立即出现
   - 后台补齐标题 / 封面 / 时长
   - `去复习` 进入正确媒体，而不是示例内容
4. 图片上传
   - 主流只看原图
   - 点击能看原图
   - 不默认出现 OCR 正文
5. 文档 / PDF / PPT
   - 主流只看原件消息
   - 点击能打开原件
   - 解析在后台，不阻塞后续输入
6. 微信服务号
   - 发文字 / 语音 / 图片 / 链接
   - 服务号回执正常
   - H5 打开后进入同一条收集流

## 10. 给下一个 agent 的工作守则

任何改动都先问这 5 句：

1. 这个改动是不是让用户更容易收集？
2. 是不是更原件优先？
3. 是不是更少打扰？
4. 是不是更像“发消息”而不是“用功能”？
5. 是不是更容易自然长出复习和 Tutor？

只要偏离这些，就说明方向跑偏了。

### 10.1 和用户沟通时要记住

用户不是在追求一个“更炫的 demo”，而是在做一个真正可能成立的产品。

所以：

- 不要只汇报细枝末节 UI
- 不要把低杠杆修改包装成高价值推进
- 要优先推进真正闭环的链路
- 要始终站在“优秀收集产品”的标准上判断

如果必须在“看起来更精致”和“让主链闭环”之间做选择，优先主链闭环。
