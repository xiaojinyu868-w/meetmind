## 1. 产品要去哪里

MeetMind 正在从"录课工具"转向**应用矩阵 + 共享学习记忆**。这是路演级的战略承诺，完整图景是：

- **应用矩阵**：课堂同桌、测验、AI 家教、论文学习、考前作战等应用，各自独立入口、独立心智、独立获客——但它们不是一堆孤立工具。
- **共享记忆**：所有应用围绕同一个人读写同一份学习记忆。"课堂暴露的问题进入家教，测验发现的薄弱点改变下一次讲解"。核心一句话：**同一个人，同一套记忆**。
- **记忆是活的**：不是流水账，而是分层的理解——当下的问题（短期）、近期的课程/错题/阶段目标（中期）、知识结构/掌握轨迹/稳定偏好（长期）。它还要记得住**变化**："曾经困惑、现在掌握"是状态迁移，不是覆盖删除。
- **越用越懂你**：每次学习都更新记忆，所以从第二次开始，AI 面对的不是一个 Prompt，而是一个有历史的人。这句话要从路演稿变成产品事实，并且**可测量**（我们把它叫 Context Lift：有记忆 vs 无记忆的体验差）。
- **终局是开放基础设施**：记忆 + 统一登录 + 支付打包成对外体系（类似观猹的统一账号打法，但多给一份可协议化读写的记忆）。第三方学习应用的开发者理想态是"给 coding agent 一行提示就能接入"——接入后他的应用也能"认识这个用户"。记忆由此成为可携带的用户资产和整个矩阵的护城河。

本次任务（P0）是这个图景的地基。

## 2. 现状的痛

现有记忆系统（学习者画像 LearnerProfile，存服务端 `User.learnerProfileJson`）是三处硬伤：

1. **只有全局问答会产生记忆**——课堂、测验、家教里发生的学习信号全部丢失；
2. **合并逻辑在客户端**——浏览器 merge 后 PATCH 全量覆盖画像：并发互踩、任何写入方能改整个画像、服务端只是哑管道；
3. **记忆上限 24 条滚动丢弃**——"有历史的人"实际只有"最近的人"。

一个关键架构事实：**Tutor/全局问答的对话不落服务端**（只存客户端 IndexedDB）；服务端能直接看到的交互只有课堂转写、微信消息、家教事件流等。"观察交互自动沉淀记忆"因此必须同时考虑客户端边缘和服务端两侧。

## 3. 本次目标与意图

**把"记住用户"改造成事件驱动、服务端收口的管线**，让记忆系统配得上上面的愿景：

- 学习信号以**事件**的形式表达和传输（来自哪个应用、什么类型、溯源到哪里），事件只增不改、全量留史、可回放重建；
- **画像从"被各路人直接改写的文件"变成"事件流的物化视图"**——写入权收口，读路径保持顺畅；
- 全局问答这条现有链路迁移到新架构上，验证端到端闭环；
- 立起**记忆质量的评测骨架**（repo 已有 SWE-bench 风格 eval harness：`tests/eval/{asr,tutor}` + `make eval-*` + regression-guard CI 门禁，照它的规矩加 memory 一份）——"记得对不对"要成为可测量、可回归的指标。

意图上多说一句：这一步既是还债（修掉三处硬伤），也是**协议的第一块基石**——内部应用先走通"事件→记忆"的协议，未来对外开放时卖的就不是纸面设计，而是被自家应用矩阵每天验证的东西。设计时请把这个终局放在心里，但本次范围以把地基做扎实为准，不要提前实现终局。

我们调研过相关开源工作（mem0 / memobase / Graphiti / Zep / Langfuse / HaluMem 等），结论供参考但**不构成约束**——你自己调研、自己判断该借鉴什么、该自建什么。
