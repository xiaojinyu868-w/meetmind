# Context 效果阶段验证：条件概率合成轨迹

> 日期：2026-09-07。历史上游样例；2026-09-08 校正证据范围。本页不是 MeetMind 应用闭环验收，也没有验证教育效果。

## 实验设置

- 数据：一条合成学习经历，不包含真实用户信息。
- 经历：学生反复混淆 `P(A|B)` 与 `P(B|A)`，最近一次选择了反向条件；Tutor 建议画概率树。
- 记忆服务：独立 Hindsight `0.9.2`，真实异步 retain、operation、recall、删除链路。
- 生成模型：服务器已有 DashScope `qwen-plus`，温度 0。旧脚本虽然都问下一步学习计划，但指令措辞不同，且未检查回答是否截断，不能按严格匹配对照解释。
- 对照变量：第一轮不给历史 Context；第二轮注入 Hindsight 返回的记忆文本。
- 清理：旧脚本尝试删除 Hindsight document 和 terminal operation，但清理错误会被吞掉，旧 `passed` 状态不能独立证明清理成功。

## 观察结果

Hindsight operation 最终状态为 `completed`，召回两条记忆：

1. Tutor 建议通过概率树帮助学生区分两个反向条件。
2. 学生反复混淆两个条件概率，并在最近一次练习中选反。

无历史 Context 时，模型给出的方向是从等可能结果、直觉和低认知负担开始，避免直接进入抽象定义。这个建议对一个完全陌生的学习者合理，但没有识别出当前学生的具体卡点。

有历史 Context 时，模型明确建议：

- 用具体场景画概率树；
- 给每条分支同时标注事件描述和条件概率符号；
- 专门对照 `P(A|B)` 与 `P(B|A)`；
- 解释为什么上次反向选择会错；
- 不宣称学生已经掌握。

## 阶段结论

这次上游诊断支持一个产品假设：Context 的价值不是让模型“记住一句话”，而是让另一个 Application 把下一步任务从泛化的入门建议变成针对当前困难的练习。需要由 MeetMind 应用链路进一步验证的闭环是：

```text
课堂 / 测验暴露困难
→ Hindsight 提取带来源的记忆
→ 另一个 Application 读取
→ 生成针对性的下一步学习动作
```

这还不是统计意义上的效果结论。当前只有一条合成轨迹、一次有无 Context 对照，而且绕过了 MeetMind 的身份、授权、worker 与控制面，尚未测量长期准确率、用户主观感受、错误记忆伤害或多 Application 连续使用。因此只保留为“上游直连样例”，不能称为“记忆系统效果已验证”。

## 下一阶段验收

MeetMind 应用闭环验收使用同一 fixture 用户的三段连续轨迹：课堂解释、测验错误、复习纠正。至少接入课堂、测验和 Tutor 三个 Application，检查：

1. Tutor 是否引用正确的困难和原始来源；
2. 纠正后的经历是否改变下一次建议；
3. 暂停或忘记后是否立即停止使用旧记忆；
4. 没有相关历史时是否保持诚实降级，不编造个性化结论。

`tests/eval/context/continuous-journey.py` 仅复现上游诊断。修订后的脚本使用同一任务与指令，仅改变历史证据字段，并要求召回非空、模型完整结束、删除成功及删除后空召回；失败以非零码退出并保留待清理标识。脚本仍不会验证上面列出的 MeetMind 控制与应用行为。

## 历史记录：三个上游文本标签（2026-09-08）

旧报告记录了 3 次 completed operation、8 条召回和删除后的 0 条召回。课堂、测验和 Tutor 只是直接写入文本的标签，没有真实应用生产者或 Tutor 路由参与；没有暂停或 MeetMind 忘记动作，也没有纠正前后的匹配比较。旧脚本的无条件通过与清理错误吞掉问题，使 `passed` 不能作为验收依据。

上述数字只保留为历史运行记录。本页不据此得出“三 Application 连续验证成立”“纠正改变了下一步建议”或“忘记后立即停止使用”的结论。新的应用报告必须提供真实 API、worker、来源和控制证据，并与本页分开记录。

## 当前产品判断

Hindsight 可以被替换，MeetMind 应持续积累的是原始学习过程、来源关系、跨应用授权协议、用户控制和“记忆如何改变教学动作”的应用经验。这里才是 Context 逐渐形成壁垒的部分。
